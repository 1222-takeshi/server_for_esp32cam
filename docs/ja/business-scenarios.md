# 事業・導入シナリオとKPI

この文書は、ESP32-CAM スナップショットサーバーを「何のために、どの状態になれば成功と判断するか」を定義します。機能追加の一覧ではなく、PoC/MVP の継続判断、優先順位、やらないことを揃えるための基準です。

## 目的

最初の導入目的は **ペット監視** です。既存の TP-Link Tapo カメラ 1 台とは異なる視点を ESP32-CAM で補い、低コスト・低メンテナンスで猫の様子を確認できる状態を目指します。

## 想定利用者

| 項目 | 内容 |
|------|------|
| 初期利用者 | 開発者本人のみ |
| 利用場所 | 自宅内 LAN を前提 |
| 初期カメラ台数 | ESP32-CAM 1 台 |
| 将来カメラ台数 | ESP32-CAM 3 台 + 既存 Tapo 1 台との連携を検討 |
| 主な閲覧方法 | Raspberry Pi 上のサーバーにブラウザでアクセス |
| 本命の運用環境 | Raspberry Pi。可能であれば Raspberry Pi Zero 系で常時稼働 |

## 主要ユースケース

### 1. 留守中・別室から猫の様子を見る

- ESP32-CAM が一定間隔でスナップショットを撮影し、サーバーへアップロードする。
- ユーザーはブラウザから最新画像と履歴を確認する。
- Tapo カメラとは異なる視点を ESP32-CAM で補い、死角を減らす。

### 2. 一週間の常時稼働性を検証する

- Raspberry Pi または Raspberry Pi Zero 上で 7 日間連続稼働させる。
- 途中でサーバー再起動・ネットワーク断・ディスク逼迫などが起きた場合も、原因確認と復旧が可能な状態にする。
- まずは「止まりにくい」「止まっても気づける」「復旧手順が分かる」ことを MVP の中心に置く。

### 3. 低コストな視点追加として ESP32-CAM を使う

- Tapo を増設する代わりに、ESP32-CAM で安価に視点を追加する。
- 月額費用は 0 円を目標にし、外部クラウド依存を避ける。
- Raspberry Pi のローカル保存を基本とし、クラウド保存や外部通知は後回しにする。

### 4. Tapo 連携の可能性を評価する

- 既存 Tapo カメラを置き換えるのではなく、ESP32-CAM と併用する。
- 将来的には同じ画面で Tapo と ESP32-CAM の状態や画像を並べることを検討する。
- Tapo 連携は、API の可否、認証方式、ローカル LAN で取得できるデータ、追加コスト、保守負荷を調査してから判断する。

### 5. 猫の動きに応じた撮影・制御へ拡張する

- まずは遠隔制御でカメラ設定や撮影タイミングを調整できるようにする。
- 次に短い動画保存や猫検知を評価する。
- その後、必要性が確認できた場合のみモーターによるトラッキング制御へ進む。

## MVP 成功条件

MVP は「高機能な監視システム」ではなく、**自宅 LAN 内で 1 台の ESP32-CAM が 1 週間安定してペット監視に使える状態**と定義します。

| KPI | MVP 目標 | 補足 |
|-----|---------|------|
| 連続稼働日数 | 7 日間 | 手動再起動なしを理想とする。OS/電源起因の停止は原因を記録する |
| カメラ台数 | ESP32-CAM 1 台 | 将来は 3 台まで拡張 |
| 撮影・アップロード成功率 | 95% 以上 | サーバーログと DB metadata から確認する |
| 最新画像確認 | ブラウザで 10 秒以内に最新状態を確認できる | 同一 LAN 内アクセス前提 |
| 復旧時間 | 15 分以内 | Runbook に従って復旧できること |
| 月額費用 | 0 円 | 既存 LAN / Raspberry Pi / ローカル保存を前提 |
| メンテナンス工数 | 週 1 回以下 | 容量確認、ログ確認、再起動確認をできるだけ自動化する |
| データ保持 | ローカル容量内で必要最小限 | 保存期間・容量上限は `docs/ja/requirements.md` の非機能要件に従う |

## 運用環境の比較

| 環境 | 位置づけ | メリット | 制約・注意点 |
|------|----------|----------|--------------|
| Raspberry Pi Zero | 第一候補 | 低消費電力・低コスト・常時稼働しやすい | CPU/メモリが小さいため、AI推論・動画処理・多数接続は厳しい可能性がある |
| Raspberry Pi 4/5 | 代替候補 | 余裕を持ってサーバー・DB・軽量推論を動かしやすい | 消費電力と本体価格は Zero より上がる |
| Mac/PC ローカル | 開発・検証用 | 開発効率が高く、テスト・デバッグしやすい | 常時稼働の本命ではない |
| クラウド | 当面対象外 | 外部からアクセスしやすい | 月額費用・セキュリティ・運用負荷が増えるため MVP では採用しない |

## 優先順位

ユーザー価値と低コスト運用を優先し、次の順で検討します。

1. **ESP32-CAM 遠隔制御**
   - 撮影間隔、解像度、再起動、設定更新などを LAN 内から調整できるようにする。
   - 現地で USB 接続や書き込みをし直す頻度を減らし、メンテナンスコストを下げる。
2. **短い動画保存**
   - 常時録画ではなく、必要な場面だけ短いクリップを保存する。
   - スナップショットでは猫の動きが分かりにくい場合の補助機能とする。
3. **AI 人物検知から猫検知への評価**
   - 既存の人検知基盤を参考に、猫検知に転用できるかを評価する。
   - Raspberry Pi Zero では重い可能性があるため、モデルサイズ・推論頻度・非同期処理を慎重に確認する。
4. **モーターによるトラッキング制御**
   - 猫検知の有用性が確認できた後に検討する。
   - 可動部の安全性、誤動作時の停止、配線、電源、耐久性を要件化してから実装する。
5. **ライブ配信**
   - スナップショットと短い動画で不足する場合に評価する。
   - Raspberry Pi Zero と ESP32-CAM の負荷、発熱、ネットワーク帯域を確認する。
6. **Webhook / LINE 等の通知**
   - 猫検知の精度が十分で、通知疲れが起きない見込みが立ってから検討する。
   - 外部サービス依存とトークン管理が増えるため、MVP では後回しにする。
7. **複数カメラ管理**
   - 初期は 1 台運用を安定化する。
   - 将来 3 台へ増やす段階で、Tapo 連携も含めて同一 UI での扱いを検討する。

## 今はやらないこと

MVP では以下を明確に対象外とします。

- 常時動画録画
- 商用 SaaS 化
- スマホアプリ化
- クラウド必須化
- インターネット公開を前提にした設計
- 多人数利用・権限管理
- 高可用クラスタ構成
- 外部通知を前提にした運用

ただし、将来の自宅外アクセスや通知を完全に否定するものではありません。まずは LAN 内・月額 0 円・低メンテナンスの MVP を優先します。

## 見直しタイミング

以下のいずれかに到達したら、この文書を更新します。

- ESP32-CAM 1 台で 7 日間連続稼働を達成したとき
- Raspberry Pi Zero での実運用が困難だと判明したとき
- Tapo 連携の技術調査結果が出たとき
- カメラを 2 台以上へ増やすとき
- 猫検知または短い動画保存を MVP 後の次フェーズに入れるとき
