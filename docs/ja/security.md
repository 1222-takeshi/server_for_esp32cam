# セキュリティガイドと脅威モデル

このドキュメントでは、ESP32-CAM スナップショットサーバーの信頼境界・主要脅威・対策状況・運用チェックリストを説明します。

---

## 信頼境界

```
[ESP32-CAM デバイス]
       ↓ X-API-Key (LAN / Wi-Fi)
[Flask サーバー (Raspberry Pi / Docker)]
       ↓ Bearer Token (LAN)
[管理ブラウザ / 管理 CLI]
       ↓
[ローカルファイルシステム / SQLite DB]
       ↓ (オプション) HTTPS
[Webhook 送信先 (外部サービス)]
```

| 境界 | 信頼レベル | 備考 |
|-----|----------|------|
| ESP32-CAM → サーバー (LAN) | デバイス認証あり | `DEVICE_API_KEY` が未設定なら認証なし。共有キー運用では `SHARED_KEY_DEVICE_ID` との完全一致も必須 |
| 管理ブラウザ → サーバー (LAN) | 管理者認証あり | `ADMIN_TOKEN` が未設定なら認証なし |
| サーバー → ファイルシステム | 信頼する | コンテナ内のみ |
| サーバー → Webhook 先 | 信頼しない | SSRF 対策は利用者責任 |
| インターネット → サーバー | **危険** | HTTPS + リバースプロキシ必須 |

## 主要脅威と対策状況

### T1: 不正アップロード（認証なし）

| 項目 | 内容 |
|-----|------|
| 脅威 | 認証なしで JPEG をアップロードされ、ストレージが枯渇する |
| 対策 | `ESP32CAM_DEVICE_API_KEY` 設定で `X-API-Key` ヘッダーを必須化し、共有キー運用では `ESP32CAM_SHARED_KEY_DEVICE_ID` と `device_id`/`camera_id` の完全一致を必須化。複数台は `ESP32CAM_DEVICE_API_KEYS` を使う |
| 設定状況 | **運用時は必須**。未設定の場合、起動時に WARNING ログが出力される |
| 残存リスク | LAN 内の他ホストが API キーを傍受できる（HTTPS 未使用時） |

### T2: アップロードレート超過 / DoS

| 項目 | 内容 |
|-----|------|
| 脅威 | 大量リクエストでサーバーを過負荷にする |
| 対策 (HTTP) | Flask-Limiter によるレート制限（デフォルト 10 回/分・デバイスキー単位） |
| 対策 (WebSocket) | フレーム間隔制限（`UPLOAD_WS_MIN_FRAME_INTERVAL_SECONDS`） |
| 対策 (接続数) | `MAX_WS_CONNECTIONS` で WebSocket 接続数を上限設定 |
| 残存リスク | 多数のデバイス（異なる API キー）からの分散攻撃は制限されない |

### T3: 悪意ある JPEG ペイロード

| 項目 | 内容 |
|-----|------|
| 脅威 | 壊れた / 巨大な画像でサーバーをクラッシュさせる、ディレクトリトラバーサル |
| 対策 | Pillow による JPEG バリデーション（形式・寸法チェック） |
| 対策 | `MAX_CONTENT_LENGTH` でペイロードサイズ制限 |
| 対策 | ファイル名はサーバー側で UUID + タイムスタンプで生成（クライアント名を使用しない） |
| 残存リスク | 低。ファイル名はユーザー入力を使わないため、パス操作のリスクは排除済み |

### T4: 管理 API への不正アクセス

| 項目 | 内容 |
|-----|------|
| 脅威 | カメラ削除・設定変更・ログ閲覧が無断で行われる |
| 対策 | `ESP32CAM_ADMIN_TOKEN` 設定で Bearer トークン認証を必須化 |
| 対策 | デバイス用 API キーと管理者トークンを分離（各役割で独立） |
| 残存リスク | **LAN 内では平文通信**。トークンが傍受される可能性あり（HTTPS 推奨） |

### T5: トークン・シークレットの漏洩

| 項目 | 内容 |
|-----|------|
| 脅威 | API キーや Admin トークンがログ・コード・PR に混入する |
| 対策 | `.env` ファイルは `.gitignore` に含まれる |
| 対策 | ログに API キーを出力しない（`log_injection` 対策済み） |
| 残存リスク | `.env.example` への実値書き込み、ファームウェアへのハードコーディング |
| 運用ルール | シークレットは Issue・PR・チャットに実値で記載しない |

### T6: 画像データの漏洩

| 項目 | 内容 |
|-----|------|
| 脅威 | プライバシーに関わる JPEG が外部に公開される |
| 対策 | `/files/<filename>` は認証なしでもアクセス可（設計上の選択） |
| 残存リスク | ファイル名を推測されると画像が公開されてしまう |
| 推奨 | LAN 内運用を前提とする。インターネット公開時は nginx で `/files/` を認証保護する |

### T7: ディスク枯渇

| 項目 | 内容 |
|-----|------|
| 脅威 | アップロードでディスクが満杯になりサーバーが停止する |
| 対策 | `STORAGE_RETENTION_MAX_BYTES` / `MAX_AGE_SECONDS` による自動削除 |
| 対策 | `/healthz/ready` のディスク残量チェックで早期検知 |
| 運用 | 使用率 85%/95% 時の対応手順: `docs/ja/operations-runbook.md` 参照 |

### T8: Webhook の誤送信・SSRF

| 項目 | 内容 |
|-----|------|
| 脅威 | 誤った URL に機密データを送信する、内部ネットワークへの SSRF |
| 対策 | Webhook は `WEBHOOK_URL` 設定時のみ有効（未設定なら無効） |
| 対策 | Webhook 送信失敗がアップロード処理を中断しない |
| 残存リスク | URL の正当性チェックは実装されていない。LAN 内 URL を設定すると内部サービスに POST される |
| 推奨 | Webhook URL は外部の HTTPS エンドポイントのみ設定する |

## ローカル LAN 運用 vs インターネット公開

| 要件 | LAN 内 | インターネット公開 |
|-----|--------|----------------|
| HTTPS | 不要 | **必須** (nginx / Caddy で終端) |
| `DEVICE_API_KEY` + デバイスID固定 | 推奨 | **必須** |
| `DEVICE_API_KEYS` (複数台) | 複数台では推奨 | 複数台では **必須** |
| `ADMIN_TOKEN` | 推奨 | **必須** |
| `/api/docs` の公開 | 可 | 公開要否を判断 (Swagger UI 資産は `/static/vendor/swagger-ui/` に自己ホストされ、外部 CDN には依存しない。#316) |
| `/files/` の認証 | 不要 | 推奨 (nginx で追加) |
| ファイアウォール | 任意 | 必須 (8080 を LAN のみに制限) |

## 運用セキュリティチェックリスト

### 初回デプロイ時

- [ ] `DEVICE_API_KEY` に 32 バイト以上のランダム値を設定する
  ```bash
  python3 -c "import secrets; print(secrets.token_hex(32))"
  ```
- [ ] 単一デバイスの共有キー運用では `ESP32CAM_SHARED_KEY_DEVICE_ID` を実機の `DEVICE_ID` に設定する
- [ ] 複数デバイスの運用では `ESP32CAM_DEVICE_API_KEYS` にデバイスごとのキーを設定し、共有キーを使い回さない
- [ ] `ADMIN_TOKEN` に 32 バイト以上のランダム値を設定する（上記コマンドを再実行）
- [ ] `.env` ファイルがバージョン管理に含まれていないことを確認する
- [ ] インターネット公開時は HTTPS を設定する

### 定期確認（月次）

- [ ] API キーを更新する（漏洩の可能性がある場合は即時更新）
- [ ] `/healthz/ready` でサーバー正常性を確認する
- [ ] ログに実際のシークレット値が含まれていないことを確認する
- [ ] ディスク使用率が 85% 未満であることを確認する

### シークレット更新手順

```bash
# 新しいキーを生成する
NEW_KEY=$(python3 -c "import secrets; print(secrets.token_hex(32))")

# .env を更新する
# ESP32CAM_DEVICE_API_KEY=<新しいキー>

# サーバーを再起動する
docker compose restart app

# デバイスファームウェアのキーを更新する（Arduino IDE / PlatformIO で書き込む）
```

## 既知の除外事項

以下は設計上の判断により現時点で対策されていません:

| 項目 | 理由 |
|-----|------|
| mTLS（クライアント証明書） | ESP32 での証明書管理コストが高い（ADR-005 参照） |
| `/files/` の認証 | LAN 内運用前提のため不要と判断 |
| Webhook URL バリデーション | 範囲外。設定は運用者の責任 |
| CSRF 対策 | ブラウザからのフォーム操作はなく API のみのため不要 |
