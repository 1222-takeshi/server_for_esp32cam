# 猫の検知から安全なカメラ追従までの能力契約

- Source: 専用の一室にいる立ち耳のScottish Foldを、夜は室内照明を消して見守るという利用要件（[#465](https://github.com/1222-takeshi/server_for_esp32cam/issues/465)）。
- Status: 設計契約。モータ制御機材・夜間撮像方式・現場データの評価結果は未確定であり、実機駆動は許可しない。
- Related: [現行ロードマップ](../ja/roadmap.md)、[高頻度撮影・認識計画](high-rate-recognition.md)、[猫検知のオフライン評価](pet-detection-evaluation.md)、[動画upload契約](video-upload.md)。

## CAPABILITY

利用者が専用の一室にいる猫を見守る際、システムは猫を検知し、その位置から画面中心までの角度誤差を計算する。十分な検知品質、フレーム鮮度、校正情報、機材の安全条件が揃った場合に限り、後続段階でカメラのpan/tiltを少しずつ動かして再観測する。最初の成果物はモータを動かさない角度推定シミュレーションとする。対象は「猫」というクラスであり、現時点で飼い猫個体の識別は約束しない。

## CONSTRAINTS

- **確定した利用条件:** 一室、立ち耳のScottish Fold、夜間の室内照明off。耳形状を特別な検知ルールや学習データの代替にしない。部屋の壁・家具・猫の行動範囲が機械的可動範囲を自動的に決めるわけではない。
- **現行の実装:** ESP32-CAMは約5秒間隔でJPEGをWebSocket送信し、サーバーは非同期で推論する。検知の `bbox` は正規化 `[x1,y1,x2,y2]`、`track_id` はnullableでプロセス内の軽量追跡状態に過ぎない。現行の人物検知成功は猫検知精度の証拠ではない。
- **撮影・認識の目標（2026-10-16合意）:** 将来の追従では1台で新規画像の撮影と猫検知推論を最低5Hz（200ms周期）、希望10Hz（100ms周期）で行う。実行基盤はRaspberry Pi単体が必須（2026-10-17訂正）。Macの[参考試験](high-rate-recognition-results.md)は受入対象外で、Piの[30分試験](raspi-high-rate-recognition-results.md)は最低5Hz技術条件pass、希望10Hzは未達。現場精度・校正・常用構成は未受入。追跡による位置補間を認識回数へ数えず、撮影→認識結果の遅延、欠落率と精度も[高頻度認識計画](high-rate-recognition.md)で別に受け入れる。
- **運転モード:** [容量制限付きmode設計](operating-modes.md)のeco/追跡準備は撮影・認識頻度を選ぶ提案で、未実装。モード切替はmotor駆動許可と別にし、反映待ち/通信断/旧世代結果ではhold、受入前はobserve_onlyを維持する。
- **鮮度の欠落:** 通常運用のWebSocket payloadはJPEG binaryのみで、サーバーの `captured_at` は受信時刻で補完される。受信時刻だけを真の撮影時刻と扱って駆動してはならない。隔離実験ではboot/frame ID、device撮影時刻、offset区間付きの鮮度判定と推論終了時刻を実装済み。通常経路への統合、物理的な時計校正と駆動時の鮮度条件は別に受け入れる。
- **暗所:** 室内照明offの夜間画像で猫が見えると仮定しない。現場で撮像可能性を確認し、必要なら対応カメラと補助照明/IRの方式、給電、猫への影響、撮影範囲を決める。モデルの再学習だけで光量不足を解決した扱いにしない。
- **駆動の既定状態は停止:** 校正・許容角・速度・電源/配線・手動停止・鮮度しきい値のどれかが未設定または不正なら、角度候補を記録してもモータ指令を出さない。想定外の人や猫との接触・挟み込みを避ける設置条件を実機試験前に確認する。

## IMPLEMENTATION CONTRACT

### Actors, surfaces, states

- 利用者/運用者は映像、検知根拠、追従状態、hold理由を閲覧し、追従を無効化・手動停止できる。管理者のみ校正・安全上限を設定できる。モデル/追跡器は観測を提案し、モータ駆動の権限を持たない。
- `disabled → observe_only → simulating` まではモータ出力なし。機材選定、校正、現場評価、安全審査を終えた後の別Issueでのみ `armed → tracking` を設計する。`tracking → hold` は猫不在、複数候補、低信頼度、暗所品質不足、古い/欠落フレーム、校正不一致、通信/推論/モータ異常で即時遷移する。`manual_stop` はラッチし、管理者の明示的な再有効化まで出力しない。
- 追従は毎フレームの連続回転を前提にしない。観測→一回の制限付き角度候補→再観測の低速closed loopを先に評価する。現在の約5秒周期にcapture/upload/inference/command/motionの遅延が加わるため、滑らかな追従や高速移動への追随を未検証のまま約束しない。

### Inputs, geometry, outputs

- 観測入力の契約: `camera_id`, `frame_id`, 信頼できる `captured_at`, `received_at`, `inferred_at`, 画像の `width/height`, 向き/反転設定, `calibration_id`, `label`, `score`, 正規化 `bbox`, nullable `track_id`, 推論状態, 暗所品質指標。既存APIの検知値を活用しつつ、存在しない時刻・品質・校正フィールドは後続Issueで設計する。元画像と正解ラベルは不変として扱う。
- `0 ≤ x1 < x2 ≤ 1`, `0 ≤ y1 < y2 ≤ 1` を満たす猫bbox一件だけを候補にする。中心は `u=(x1+x2)/2`, `v=(y1+y2)/2`。画像中心との差は `u−c_x/W`, `v−c_y/H`（`c_x,c_y` は校正済み主点、`W,H` は画像寸法）。既知の焦点距離 `f_x,f_y` を画素で表すと、カメラ座標の角度誤差（度）は `pan_error_deg=atan((uW−c_x)/f_x)×180/π`, `tilt_error_deg=atan((vH−c_y)/f_y)×180/π`。実測の水平FOVしかない初期シミュレーションでは `f_x≈W/(2tan(HFOV_rad/2))`（`HFOV_rad` はラジアン）を暫定値にできるが、レンズ歪みや反転を含む校正と実測で確かめる。モータのpan/tiltの符号・ゼロ点への写像は機材設置後に決める。[OpenCVのpinhole model](https://docs.opencv.org/doc/doxygen/html/d4/d93/group__calib.html) に基づく近似であり、FOV値だけを推測してモータ角度に直結しない。
- シミュレーション出力は `frame_id`, `candidate_id`, `pan_error_deg`, `tilt_error_deg`, `valid/hold_reason`, `calibration_id`, 計算時刻、使用したbbox/scoreを持つ。無効なbbox、NaN、寸法0、校正欠落、未来/古い時刻、猫以外、複数猫、低信頼度、暗所品質不足なら `hold` として角度指令を生成しない。候補選択のしきい値と複数猫の扱いは現場評価前に固定する。
- 後続の実機指令は設定済みの角度範囲、最大速度/加速度、deadband、一回の最大移動量、更新間隔、停止スイッチを全て満たす場合だけ発行する。制限値は機材仕様と実測から決める。再送・順序逆転・古い `frame_id` で重複移動しないよう、指令IDとACK/timeout、停止時の電気的挙動を契約化する。

### Data, security, observability, acceptance

- 画像・モデル・ラベル・正解manifest・評価結果は[評価手順](pet-detection-evaluation.md)に従いGit外に保管し、撮影セッション単位で開発/保留評価を分割する。昼、照明offの夜、猫の距離/向き/遮蔽、空室、人、他動物、影を含める。対象はまず猫クラスの検知であり、個体識別が必要なら別のデータ/同意/評価契約を作る。
- `camera_id` と校正/指令の紐付けを検証し、外部入力をそのまま角度にしない。既存の管理者/デバイス認証を踏まえ、駆動権限と手動停止の監査ログを別Issueで定義する。画像の保存期間・アクセス制御は既存の運用方針を守る。
- 記録する指標: 昼夜別の猫検知precision/recallと誤検知・見逃し、brightness/画質の棄却率、capture-to-inference-to-decisionのp50/p95、hold理由、シミュレーション角度誤差、実機段階では指令/ACK/停止/上限到達と猫を中心に戻すまでの時間。しきい値は保留評価画像を見る前に承認し、結果に合わせてsilent tuningしない。
- 受入順序: (1)夜間の撮像方式と機材を決定、(2)現場GTで昼夜の猫検知を評価、(3)時刻/フレーム鮮度を実装して検証、(4)校正画像とシミュレーションで角度符号・誤差を検証、(5)モータを外した状態で境界/故障注入、(6)物理停止可能な環境で低速実機試験。各段階で失敗ならobserve_onlyへ戻す。
- 高頻度撮影・認識の開発はモータなしで進められる。駆動前に最低5Hzの連続試験と事前固定した遅延・鮮度・精度の条件を満たす。10Hzは希望目標として別判定し、5Hz合格で達成した扱いにしない。認識Hzはモータ指令Hzを意味せず、指令周期は機材と制御・停止条件から別に決める。
- シミュレーションの最小テスト: 正常な一件の猫bboxで期待する角度符号、画面中心付近でdeadband内、画像端でも上限内、無効bbox/欠落校正/不正時刻でhold、前フレームの検知が遅れて到着しても新しい指令を上書きしないことを検証する。夜間画質不足と複数候補もholdの回帰ケースにする。

## NON-GOALS

この設計PRは猫検知モデルの切替、夜間照明/IR機材の購入、個体識別、サーボ配線やモータ駆動API、動画生成、通知連携、複数室対応を実装しない。既存の[動画upload設計](video-upload.md)のリンクとスコープは維持する。

## OPEN QUESTIONS

1. 使用するpan/tilt台、可動範囲、給電、機械的停止、物理的な手動停止、カメラ/レンズの型番と実測FOVは何か。
2. 照明offの夜に、既存ESP32-CAMで猫が判別できるか。補助照明/IRを使う場合、対応センサ、波長・光量、設置と猫への影響をどう確認するか。
3. 部屋に猫が一匹だけいる運用を保証するか。人/他動物/複数候補が現れた際の選択と停止条件は何か。飼い猫個体の識別が必要か。
4. 許容する画面中心誤差、追従遅延、猫の移動速度、夜間の検知品質、鮮度TTL、モータの速度/角度上限をどの試験結果で決めるか。
5. WebSocket画像に撮影時刻・連番をどう添付し、デバイス時計のずれ/再起動/遅延をどう扱うか。

## HANDOFF

現時点では製品/機材の確認と安全設計レビューが先。次の独立Issueは夜間撮像・現場GT取得、フレーム鮮度契約、校正とモータなし角度シミュレーションに分ける。各受入ゲートを満たしてから、実機駆動のIssueでテスト駆動開発と検証ループへ進む。
